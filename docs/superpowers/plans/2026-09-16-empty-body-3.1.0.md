# apify 3.1.0 — Empty-body contract (additive half) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give consumers a way to declare a bodyless endpoint, start detecting the empty-JSON-body case, and pin the last guard 3.0.0 shipped untested.

**Architecture:** Everything here is additive — nothing that works today stops working. `parseResponse` gains a `'none'` branch and starts reporting emptiness through a sentinel; the success path warns once per request name and keeps returning `null`. 4.0.0 later changes two lines at that one seam to make it an error. The share test closes a coverage gap and touches no source.

**Tech Stack:** TypeScript 5.8 (strict, ES2020, `moduleResolution: bundler`), vitest 3.2 with `--typecheck`, zero runtime dependencies, pure ESM.

**Spec:** [`docs/superpowers/specs/2026-09-16-empty-body-contract-design.md`](../specs/2026-09-16-empty-body-contract-design.md)

## Global Constraints

- **Zero runtime dependencies.** Nothing may be added to `dependencies`.

- **Runtime-agnostic.** Nothing above the `node >= 20` floor. **`AbortSignal.any` and regex lookbehind are banned.** `console` is guarded — the codebase already avoids `performance` for the same reason.
- **`src/index.ts` exports no utils or internals.** `EMPTY_JSON_BODY` stays module-private.
- **This release is additive.** No existing behaviour changes. If a pre-existing test needs editing, something is wrong — stop and report.

- [ ] **Step 7: Prototype the type-level guard**

The problem: `new Request<P, User>({ responseType: 'none' })` would put `data: undefined` behind a `User`, which is the class of lie this release exists to remove.

`src/request.ts` currently imports only `RequestConfig` (`import type { RequestConfig } from './types.js'`). The guard references `ResponseType`, so widen that import first:

```ts
import type { RequestConfig, ResponseType } from './types.js'
```

Then make the constructor's parameter conditional on `TResponse`:

```ts
  constructor(
    config: [TResponse] extends [undefined]
      ? RequestConfig
      : RequestConfig & { responseType?: Exclude<ResponseType, 'none'> }
  ) {
```

Read as: a request whose response type is `undefined` may declare anything, including `'none'`; any other request may not declare `'none'`.

**Verify all four shapes before keeping it:**

| expression | expected |
|---|---|
| `new Request<P, undefined>({ …, responseType: 'none' })` | compiles |
| `new Request<P, User>({ …, responseType: 'none' })` | **error** |
| `new Request<P, User>({ …, responseType: 'json' })` | compiles |
| `new Request<P, User>({ … })` (omitted) | compiles |

Also check `new Request({ … })` with no explicit generics still compiles for a normal request — `TResponse` infers as `unknown`, and `[unknown] extends [undefined]` is false, so it takes the restricted branch. That is acceptable (a bare `'none'` without explicit typing is refused, which is the point) but **must not** break any existing call site.

**If the guard cannot be made to work without contorting `RequestConfig` or breaking inference elsewhere, drop it** — return `constructor(config: RequestConfig)` to its original form, document the convention in the `responseType` JSDoc instead ("declare `TResponse` as `undefined` when using `'none'`"), and **say so explicitly in your report**. Do not leave a half-working guard in place.

### Task 2: Detect the empty JSON body, and warn once

**Files:**
- Modify: `src/create-api.ts` (`parseResponse`'s json branch, the per-instance state block, the success path)
- Test: `tests/empty-body.test.ts` (create)

**Interfaces:**
- Consumes: Task 1's `parseResponse` switch (adds to its `json` branch, does not alter `'none'`).
- Produces: module-private `const EMPTY_JSON_BODY: unique symbol`, and a per-`createApi` `warnEmptyBodyOnce(name: string): void`. **4.0.0 replaces two lines at the success-path seam and nothing else.**

**Why a sentinel and not `data === null`:** `JSON.parse("null")` is `null`. A server sending the body `null` is indistinguishable from one sending nothing, and erroring on the former in 4.0.0 would be wrong — `null` is valid JSON. The sentinel is what keeps those two apart.

- [ ] **Step 4: Add the per-instance warn-once**

In `src/create-api.ts`, immediately after `const shareTracker = new ShareTracker()`:

```ts
  // ---------------------------------------------------------------------------
  // Empty-body warning — one per request name, per API instance, same
  // per-createApi lifetime as the trackers above so two instances warn
  // independently and nothing leaks across them.
  //
  // Transitional: 4.0.0 makes an empty JSON body an error and this goes with
  // it. It exists because the consumers most at risk are the ones who upgrade
  // without reading a changelog, and it names the exact Request to change.
  // ---------------------------------------------------------------------------
  const emptyBodyWarned = new Set<string>()

  const warnEmptyBodyOnce = (name: string): void => {
    if (emptyBodyWarned.has(name)) return
    emptyBodyWarned.add(name)
    try {
      if (typeof console !== 'undefined' && typeof console.warn === 'function') {
        console.warn(
          `[apify] ${name}: server returned an empty body for responseType 'json'. ` +
          `This yields data: null today and will be an error in 4.0.0. ` +
          `Declare responseType: 'none' if the endpoint returns no content.`
        )
      }
    } catch {
      /* a diagnostic must never fail a request — same stance as fireOnError */
    }
  }
```

**The gap:** `src/create-api.ts` re-merges `sharedSignal` into `ctx.request.signal` when a middleware has replaced it. Deleting those three lines leaves the entire suite green — yet without them, a `share: true` request whose middleware installs its own signal is detached from the refcount, so every sharer giving up no longer aborts it. With `retryMiddleware` in the chain it keeps retrying in the background after every caller has resolved (measured: 47 fetches against an expected 3).

**Do not assert the fetch count.** Counting over time needs a sleep and can flake. Assert the *state*: did the shared controller's abort actually reach `fetch`?

- [ ] **Step 1: Write the failing test**

```ts
  // -------------------------------------------------------------------------
  // The shared controller reaches fetch only through ctx.request.signal. A
  // middleware that REPLACES that field — the per-attempt-timeout pattern the
  // library documents — drops it, detaching the real request from the
  // refcount: every sharer giving up no longer aborts it, and with
  // retryMiddleware it keeps retrying in the background after all callers have
  // resolved. create-api.ts re-merges the shared signal in core() for exactly
  // this reason, and nothing pinned that until now.
  //
  // Asserted as state, not as a fetch count: counting retries over time needs
  // a sleep and flakes. Whether the abort actually reached fetch is decidable
  // immediately.
  // -------------------------------------------------------------------------
  it('keeps the shared controller attached when a middleware replaces the signal', async () => {
    let fetchAborted = false
    vi.stubGlobal('fetch', vi.fn((_u: string, init: RequestInit) => new Promise<Response>((_res, rej) => {
      const s = init.signal as AbortSignal | undefined
      if (s?.aborted) { fetchAborted = true; rej(s.reason); return }
      s?.addEventListener('abort', () => { fetchAborted = true; rej(s.reason) }, { once: true })
    })))

    // Installs its own signal, exactly as a per-attempt timeout would.
    const replacesSignal: Middleware = (ctx, next) => {
      ctx.request.signal = new AbortController().signal
      return next()
    }

    const api = createApi({
      baseUrl: '',
      requests: {
        get: new Request<{ id: string }, { ok: number }>({
          method: 'GET', path: '/x/:id', share: true, middleware: [replacesSignal],
        }),
      },
    })

    const a = new AbortController()
    const b = new AbortController()
    const first = api.get({ id: '1' }, { signal: a.signal })
    const second = api.get({ id: '1' }, { signal: b.signal })
    await Promise.resolve()

    a.abort()
    b.abort()
    await first.catch(() => {})
    await second.catch(() => {})
    await flush()

    // Every sharer gave up, so the shared request must have been aborted.
    expect(fetchAborted).toBe(true)
  })
```
