# apify 3.0.0 — Breaking Fixes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the `Result` type tell the truth, give `ApiError` a discriminator that separates HTTP failures from network failures from aborts from parse failures, and stop discarding data the server actually sent.

**Architecture:** Two PRs. PR-4 is types-only — `Result` becomes a discriminated union and `Request` gains phantom generics; no runtime code changes. PR-5 changes error behaviour — a new `ApiError.kind` field drives parse-error handling, abort suppression in `onError`, and GraphQL partial-data recovery. PR-4 must land before PR-5, because PR-5's new error paths are written against the union.

**Tech Stack:** TypeScript 5.8 (strict, ES2020, `moduleResolution: bundler`), vitest 3.2, zero runtime dependencies, pure ESM.

**Spec:** [`docs/FIXES.md`](../../FIXES.md) — issues #1, #5, #6, #7, #10, #11.

**Prerequisite:** [`2026-09-13-fixes-2.1.0.md`](./2026-09-13-fixes-2.1.0.md) must be merged first. PR-5 Task 13 depends on `ctx.request.signal` from that plan's Task 7.

- **Zero runtime dependencies.** Nothing may be added to `dependencies`.
- **Never throws.** Every public entry point returns a `Result`.
- **Pure ESM.** Internal imports use `.js` extensions.

### Task 9: Make `Result` a discriminated union

**Files:**
- Modify: `src/types.ts:194-215`
- Modify: `src/index.ts:30-38` (export the two members)
- Test: `tests/result.test.ts`, new `tests/types.test-d.ts`

**Interfaces:**
- Consumes: nothing.
- Produces:
  - `SuccessResult<T> = { data: T; error: null; response: Response; retry: () => Promise<Result<T>> }`
  - `ErrorResult<T> = { data: null; error: ApiError; response: Response | null; retry: () => Promise<Result<T>> }`
  - `Result<T> = SuccessResult<T> | ErrorResult<T>`
  - Task 10 and all of PR-5 are written against these.

**The bug:** `data` and `error` are independent nullable fields, so narrowing on `error` never narrows `data`. The README's headline example at `README.md:226` does not compile — verified: `error TS18047: 'data' is possibly 'null'`.

**Verified design:** the union shape below was prototyped against all three usage patterns (destructured early-return, `if (r.error === null)`, and `response.status` on success) and all three narrow correctly.

**Deliberate trade-off — `SuccessResult.response` is non-null.** This gives callers `response.status` with no null check on the success path, which is the common case. The cost: middleware that *synthesises* a success Result must supply a `Response`. Our own `cacheMiddleware` stores the full Result including its response, so it is unaffected. Third-party middleware that fabricates results will need `new Response(JSON.stringify(data))` — cheap, standard, and more correct. This must appear in the migration guide.

In `src/types.ts`, replace the whole `export interface Result<TResponse> { ... }` block (lines 194-215) with:

```ts
/**
 * A successful API call. `data` is populated, `error` is `null`, and the raw
 * `Response` is always present because the server responded.
 *
 * @typeParam TResponse - The shape of the successful response data.
 */
export interface SuccessResult<TResponse> {
  /** The parsed response data. Never `null` on this branch. */
  data: TResponse

  /** Always `null` — this is the discriminant that narrows `data`. */
  error: null

  /**
   * The raw fetch `Response`. Always present on success.
   *
   * **Note:** the body has already been consumed to produce `data`. Reading
   * `response.json()` or `.text()` will throw "Body has already been read".
   * Use `data`; `response` is for status, headers and redirect metadata.
   */
  response: Response

  /** Re-execute this request through the full middleware chain. */
  retry: () => Promise<Result<TResponse>>
}

/**
 * A failed API call. `error` is populated and `data` is `null`.
 *
 * `response` is present for HTTP and parse failures (the server responded) and
 * `null` for network failures and aborts (no response exists). Check
 * {@link ApiError.kind} to tell them apart.
 *
 * @typeParam TResponse - The expected response type. `data` is `null` here.
 */
export interface ErrorResult<TResponse> {
  /** Always `null` on this branch. */
  data: null

  /** Structured error details. Never `null` on this branch. */
  error: ApiError

  /**
   * The raw fetch `Response`, or `null` when no HTTP response exists
   * (network errors, aborts).
   *
   * **Note:** where present, the body has already been consumed.
   */
  response: Response | null

  /** Re-execute this request through the full middleware chain. */
  retry: () => Promise<Result<TResponse>>
}

/**
 * The result of every API call — a discriminated union on `error`.
 *
 * Checking `error` narrows `data`: after `if (error) return`, `data` is
 * `TResponse`, not `TResponse | null`. This is the whole point of returning a
 * result instead of throwing — the check *is* the narrowing.
 *
 * @typeParam TResponse - The shape of the successful response data.
 *
 * @example
 * ```ts
 * const { data, error } = await api.getUser({ id: '42' })
 * if (error) {
 *   if (error.kind === 'abort') return          // we cancelled it ourselves
 *   console.error(error.status, error.body)
 *   return
 * }
 * console.log(data.name)   // data is User
 * ```
 */
export type Result<TResponse> = SuccessResult<TResponse> | ErrorResult<TResponse>
```

/**
 * Detects whether a thrown value is an abort rather than a genuine network
 * failure. Both surface from `fetch` as a rejection with no HTTP response, so
 * without this check they are indistinguishable.
 *
 * Runtimes disagree on the exact class: browsers and Node throw a
 * `DOMException` named `AbortError`, `AbortSignal.timeout()` throws one named
 * `TimeoutError`, and some edge runtimes throw a plain `Error` with the same
 * name. Matching on `.name` covers all of them without a runtime assumption.
 */
export function isAbortError(err: unknown): boolean {
  if (typeof err !== 'object' || err === null) return false
  const name = (err as { name?: unknown }).name
  return name === 'AbortError' || name === 'TimeoutError'
}
```

Import it in `src/create-api.ts` and `src/graphql.ts`.

### Task 13: Stop firing `onError` for self-inflicted aborts

**Files:**
- Modify: `src/create-api.ts:520-523`
- Modify: `src/graphql.ts:184`
- Modify: `src/types.ts:413` (`ApiConfig.onError` docs) and `GraphQLBaseConfig.onError`

**Interfaces:**
- Consumes: Task 11's `kind`. Produces: `onError` is not called when `error.kind === 'abort'`.

**The bug:** every dedupe cancellation reaches the global `onError` — i.e. Sentry — as an error, when the library caused it deliberately.

**Design note:** aborts are suppressed unconditionally rather than behind a config flag. A caller who genuinely wants to observe cancellations already gets the `ErrorResult` back from the call itself; `onError` is the *reporting* hook, and reporting your own cancellations is never what anyone wants.
