# apify 2.2.0 — "Capabilities" Design

**Date:** 2026-09-13
**Status:** approved, ready for planning
**Scope:** four additive features from [`docs/FEATURES.md`](../../FEATURES.md) — #2 timeout, #3 retry policy, #4 in-flight coalescing, #10 testing entry point — plus one prerequisite.

**Companion:** [`2026-09-13-fixes-3.0.0.md`](../plans/2026-09-13-fixes-3.0.0.md) is the next release after this one and carries the breaking work (features #1 and #5, plus the six breaking audit fixes). This spec must not depend on anything in it.

---

## Goal

Ship the four features that need no breaking change, so they reach users without waiting on 3.0.0 — and fix a retry implementation that currently behaves badly enough to hurt the servers it talks to.

## Why these four, and why now

The audit proposed ten features. Seven were selected; of those, #1 (path inference) and #5 (schema validation) are deferred to 3.0.0 because #1 is breaking and #5 co-designs with 3.0.0's `error.kind` discriminator. #8 (pagination) is deferred because its iterator yields `Result`s and `Result` becomes a discriminated union in 3.0.0 — designing against the old shape then migrating would be wasted work.

That leaves four features that are purely additive. Holding them behind a major release would delay them for no benefit. One of them — #3 — is closer to a bug fix than a feature: `retryMiddleware(3)` currently fires four requests in the same tick at a server that is already failing (measured: **4 attempts took 0 ms**), with no backoff, no jitter and no `Retry-After` handling.

## Non-goals

- Anything breaking. Public types and runtime behaviour visible to existing consumers must not change. `retryMiddleware(3)` keeps compiling and keeps its meaning.
- Features #6 (`api.extend`), #7 (URL introspection) and #9 (streaming/SSE) — not selected.
- Changing the default `retryOn` behaviour. It stays 5xx-only; see Feature 3.

## Global constraints

- **Zero runtime dependencies.** Nothing may be added to `dependencies`, including test-runner packages in the new testing entry point.
- **Never throws.** Every public entry point returns a `Result`. The one exception is `createApi` itself, which may throw on invalid configuration at construction time (see Feature 4) — that is setup, not a request.
- **Pure ESM**, `.js` extensions on internal imports.
- **Runtime-agnostic.** No API with a runtime floor above the declared `engines` (`node >= 20`) or above the browser support the README claims. This rules out `AbortSignal.any` (see Foundation).
- **`src/index.ts` does not export utils or internals.** New utilities stay unexported from the barrel.
- Test commands: `npm run test:run`, `npm run test:integration`, `npm run typecheck`, and the new `npm run test:types`.

## Prerequisite — close the typecheck gap

**This lands first, alone, before any feature work.**

Nothing currently catches a type regression: `tests/` is excluded from `tsconfig.json` and vitest does not typecheck. That is how 2.1.0 briefly shipped a required `signal` key on `MiddlewareContext` that broke compilation for any consumer constructing one to test their own middleware — caught only by the whole-branch review.

This release adds generics to `RequestConfig`, and 3.0.0 is almost entirely type changes. The gap must close first.

- **Create** `tsconfig.test.json` — extends the base config, includes `tests/`.
- **Create** `tests/types.test-d.ts` — vitest `expectTypeOf` assertions covering: `Result` narrowing on `error`, params inference on API methods, `CallOptions` accepting `timeout`, and a `MiddlewareContext` literal constructed the way a consumer would (the exact regression above).
- **Add** `"test:types": "vitest run --typecheck"` to `package.json`.
- **Wire** it into `.github/workflows/ci.yml` and `prepublishOnly`, in both cases after `typecheck` and before `test:run`.

## Foundation

Two pieces shared by several features, designed once.

### `anySignal` — hand-rolled signal composition

**Create** `src/utils/any-signal.ts`:

```ts
export function anySignal(signals: (AbortSignal | undefined)[]): AbortSignal | undefined
```

Behaviour:
- No defined signals → returns `undefined`, allocating no controller (the common path stays free).
- Exactly one defined signal → returns it directly, again allocating nothing.
- Two or more → a fresh `AbortController` that aborts when the first input aborts, **propagating that input's `reason`**. Preserving the reason is what lets a `TimeoutError` stay distinguishable from an `AbortError` downstream; Feature 2's error model depends on it.
- An already-aborted input aborts the result immediately.
- Listeners are registered with `{ once: true }`.

**Not `AbortSignal.any`.** It requires Node 20.3+ while `engines` declares `>= 20`, and Chrome 116 / Safari 17.4 / Firefox 124 in browsers. *Runtime-agnostic* is a stated pillar, and 2.1.0 already replaced a regex lookbehind for the same reason (Safari < 16.4 raises a `SyntaxError` that kills the whole module). The hand-rolled version has no floor.

**Refactor** `src/utils/dedupe.ts` to use it. `DedupeTracker.track()` currently hand-merges an external signal inline; that logic moves into `anySignal` so there is one implementation. Its existing behaviour — including the identity-aware `clear()` fixed in 2.1.0 — must not change, and `tests/dedupe.test.ts`, `tests/dedupe-race.test.ts`, `tests/dedupe-cache.test.ts` and `tests/dedupe-signal.test.ts` must all keep passing untouched.

### `ApiError.kind` — pulled forward from 3.0.0, as optional

**Modify** `src/result.ts` and `src/types.ts`:

```ts
export type ApiErrorKind = 'http' | 'network' | 'abort' | 'timeout' | 'parse'
```

Added to `ApiErrorOptions` and the `ApiError` class as **optional** (`kind?: ApiErrorKind`), making it purely additive. 3.0.0 tightens it to required; that tightening is breaking only for code constructing `ApiError` directly.

The library populates it at every construction site:

| Cause | `kind` |
|---|---|
| Non-2xx response | `'http'` |
| `fetch` threw, not an abort | `'network'` |
| Caller's signal aborted | `'abort'` |
| Dedupe superseded the request | `'abort'` |
| Timeout expired | `'timeout'` |
| Response body failed to parse | **not emitted in 2.2.0** — see below |

`'parse'` is **declared in the type but never produced by 2.2.0.** It is declared now, rather than added in 3.0.0, because widening a union later would break exhaustive `switch` statements in consumer code — a silent breaking change disguised as an addition. Emitting it requires distinguishing a `SyntaxError` from `JSON.parse` from a `TypeError` from `fetch` inside the same catch block, which is fragile and which no 2.2.0 feature needs. 3.0.0 restructures that catch and starts emitting it.

**Create** `src/utils/is-abort-error.ts` — detects aborts by `name`, since runtimes disagree on the class:

```ts
export function abortKind(err: unknown): 'abort' | 'timeout' | null
```

Returns `'timeout'` for `TimeoutError`, `'abort'` for `AbortError`, and `null` otherwise. Matching on `.name` rather than `instanceof DOMException` covers browsers, Node and edge runtimes uniformly.

**Why pull it forward:** a timeout currently surfaces as `status: 0` with a `DOMException` in `error.body`, indistinguishable from the user being offline without inspecting an `unknown`. Shipping a timeout feature with no way to detect a timeout is half a feature.

## Feature 2 — Timeout

### Configuration

- `RequestConfig.timeout?: number` — per endpoint
- `CallOptions.timeout?: number` — per call, overrides the endpoint
- `OperationConfig.timeout?: number` — the GraphQL client gets the same option

Milliseconds. Non-positive or omitted means no timeout. Per-call beats per-request, matching how `headers` and `middleware` already layer.

### Semantics: whole-operation deadline

The timeout signal is created **once per `execute()`**, at context construction:

```ts
signal: anySignal([options.signal, timeoutMs > 0 ? AbortSignal.timeout(timeoutMs) : undefined])
```

Because `execute()` wraps the entire middleware chain, `timeout: 5000` means *an answer within 5s* — retries and their backoff all draw from one budget. This differs from axios, XHR and `got`, which apply timeouts per attempt.

Rationale: it is the only version where a caller can reason about worst-case latency, and the surprise for someone expecting per-attempt behaviour is bounded and in the safe direction (shorter, never longer).

Per-attempt timeouts remain available in userland, using the signal-replacing middleware that 2.1.0 enabled, placed inside the retry middleware:

```ts
middleware: [retryMiddleware(3), timeoutPerAttempt(5000)]
```

`result.retry()` re-enters `execute()` and therefore gets a **fresh** budget — a manual retry is a new operation, not a continuation.

### Composition

The merge chain needs no special-casing, given the ordering established in 2.1.0:

1. Context is built with `anySignal([callerSignal, timeoutSignal])`.
2. Middleware may replace `ctx.request.signal` wholesale.
3. `core()` seeds dedupe from `ctx.request.signal ?? callerSignal`, so the timeout survives into the dedupe-merged signal.

### Error surface

`AbortSignal.timeout()` aborts with a `DOMException` named `TimeoutError`, which `abortKind` maps to `kind: 'timeout'` — deliberately **not** `'abort'`.

This distinction is load-bearing. 3.0.0 suppresses `onError` for `kind === 'abort'`, because self-inflicted cancellations are reporting noise. A timeout is the opposite: a genuine failure that belongs in an error tracker. Collapsing the two would make 3.0.0 silently swallow every timeout.

### Documentation requirements

Explicitly requested, and not optional:

- **README** — a section stating that `timeout` is a whole-operation deadline covering retries and backoff, **naming axios as the contrasting precedent**, and showing the per-attempt recipe for readers who want that instead.
- **JSDoc** on `RequestConfig.timeout` and `CallOptions.timeout` carrying the same statement, so it is visible on hover without opening the README.
- **MIGRATION.md** — no entry needed; the feature is additive.

### Tests

`timeout` fires and produces `kind: 'timeout'`; a fast response is unaffected; per-call overrides per-request; `timeout` + `dedupe: true` (the combination that hung before 2.1.0); `timeout` + retry proving one shared budget rather than per-attempt; a caller signal aborting before the timeout yields `kind: 'abort'`, not `'timeout'`; `retry()` gets a fresh budget; `timeout: 0` and omitted both mean no timeout.

## Feature 3 — Retry policy

### Signature

```ts
retryMiddleware(3)                 // unchanged meaning, still compiles
retryMiddleware({ max: 3, ... })   // new
```

Accepts `number | RetryOptions`. The only behavioural change for existing call sites is that retries are no longer instantaneous — which is the defect being fixed.

| Option | Default | Meaning |
|---|---|---|
| `max` | `3` | Additional attempts after the first |
| `delay` | `'exponential'` | `'exponential'`, `'linear'`, or `(attempt: number) => number` |
| `baseDelay` | `250` | First delay, ms |
| `maxDelay` | `30_000` | Per-delay cap, ms |
| `jitter` | `true` | Full jitter — uniform random in `[0, computed]` |
| `respectRetryAfter` | `true` | Honour the header when present |
| `retryOn` | `r => (r.error?.status ?? 0) >= 500` | `(result: Result<unknown>, attempt: number) => boolean` |
| `onRetry` | — | `(info: RetryInfo) => void`, observational |

`attempt` is 1-based and counts retries, so the first retry is `attempt === 1`.

Full jitter rather than equal jitter: it is AWS's recommendation, and de-synchronising a herd is the entire point.

### Abortable delay

The subtle part, and the reason Features 2 and 3 want designing together. With deadline timeouts, a naive sleep can outlive the deadline — an 8s backoff under a 5s budget would idle for 3s past the point the caller gave up. So the delay observes the current signal:

```ts
function delay(ms: number, signal?: AbortSignal): Promise<void> {
  return new Promise(resolve => {
    if (signal?.aborted) return resolve()
    const t = setTimeout(resolve, ms)
    signal?.addEventListener('abort', () => { clearTimeout(t); resolve() }, { once: true })
  })
}
```

It **resolves** rather than rejects on abort; the loop then re-checks the signal and stops. No exception to thread through a middleware that must not throw.

**Pinned behaviour:** if the deadline fires during backoff, the caller receives the **last real result** — typically the 503 that triggered the retry — not a synthetic timeout error. That is the most informative thing actually observed, and it explains why retries were happening. `onError` still fires (`kind: 'http'`), so nothing is swallowed. This must be documented, because "I set a timeout and got a 503" needs an explanation.

### `Retry-After`

When present and `respectRetryAfter` is on, it **replaces** the computed delay, still capped by `maxDelay`. Both wire formats are supported: delta-seconds (`Retry-After: 120`) and HTTP-date (`Retry-After: Wed, 21 Oct 2026 07:28:00 GMT`). An unparseable or past-dated value falls back to the computed delay rather than throwing.

### `onRetry`

Fired **after** the delay is computed and **before** it elapses, so a UI can show how long the wait is, not merely that one exists:

```ts
interface RetryInfo {
  attempt: number              // 1-based
  max: number
  delay: number                // ms, after jitter and Retry-After
  result: Result<unknown>      // the result that triggered this retry
}
```

Purely observational — the return value is ignored, and the call is wrapped in a try/catch so a throwing callback cannot fail the request. A logging hook must never be able to break the chain.

This exists because the call site observes nothing during retries. `await api.call()` stays pending through every attempt and resolves exactly once; there is no intermediate state where `data` is null-but-retrying. That single-Result contract is a deliberate strength, but it leaves progress reporting with nowhere to go — `onRetry` is that place.

### Defaults

`retryOn` stays 5xx-only. Adding 429 or network errors to the default would change behaviour in a minor release for anyone upgrading without reading. Both stay documented one-liners:

```ts
retryMiddleware({ retryOn: r => r.error?.status === 429 || (r.error?.status ?? 0) >= 500 })
retryMiddleware({ retryOn: r => r.error?.kind === 'network' })
```

### Tests

Backoff actually elapses, asserting the delay sequence with fake timers; jitter stays within `[0, computed]`; `Retry-After` wins over the computed delay in both wire formats; an unparseable header falls back; `retryOn` gates correctly and receives the attempt number; `onRetry` fires once per retry with accurate `delay`, and a throwing `onRetry` does not fail the request; **abort during backoff stops promptly** rather than sleeping out the delay; `retryMiddleware(3)` behaves as before apart from timing.

## Feature 4 — In-flight coalescing

```ts
new Request({ method: 'GET', path: '/me', share: true })
```

Three identical simultaneous GETs currently make three network calls; `share` makes them make one. Sibling of `dedupe`, not a replacement: **dedupe cancels the old, share joins the existing.**

### Mutual exclusion

`dedupe: true` and `share: true` on the same `Request` **throws at `createApi` time**, before any request runs. They express opposite intents, and any combined semantics would be invention. This is the one sanctioned throw outside a `Result`: it is construction-time configuration validation, not a request failure. The message must name the offending request key.

### Identity

Keyed on `requestName` + `stableStringify(params)`. The helper already exists in `src/utils/cache.ts`, already sorts keys recursively and already distinguishes `null` from `undefined`. `cacheMiddleware` uses the same scheme, so the two features agree on what "the same call" means.

**Create** `src/utils/share.ts` with a `ShareTracker` holding `Map<string, { promise: Promise<Result<unknown>>; controller: AbortController; refs: number }>`.

### Placement — around `execute()`, not inside `core()`

Deliberately unlike dedupe, which registers inside `core()` so a short-circuiting middleware cannot cancel a live request. Coalescing wraps the whole chain so that ten callers run the middleware **once** — that is the actual saving, since ten auth injections and ten cache lookups for one network call would be most of the cost.

Consequence: all sharers receive the **same Result object**. Consistent with the existing contract, where `response`'s body is already consumed and Results are read rather than mutated.

### Per-call options — two rules, one principle

> Options that change **what is requested** break sharing. Options that change **who is still waiting** do not.

- **`headers` or `middleware` present → no sharing.** That call makes its own request. Handing caller B the response to caller A's differently-authenticated request is a bug that costs a day to find. Predictable and explainable.
- **`signal` present → shares, with refcounting.** Signals are lifecycle, not content, and React cleanup passes one on nearly every call; disabling sharing for them would make the feature useless in the codebases that want it most.
- **Per-call `timeout` present → shares**, and is observed per-caller exactly like a signal. A caller's timeout bounds *that caller's* wait, not the shared request: if A joins with a 5s budget and B with 1s, B receives a `kind: 'timeout'` Result at 1s while A's request continues. Per-**request** `timeout` (on `RequestConfig`) is a property of the operation itself and is therefore shared by all callers. This follows directly from the principle above — a timeout is patience, not content.

Refcount semantics:
- Each caller's signal is observed for **their own** Result — aborting yields that caller an abort Result immediately.
- The shared request continues for everyone else.
- Only when the **last** sharer aborts is the underlying fetch aborted.

One component unmounting must never cancel a request nine others are waiting on.

### `retry()` and cleanup

`retry()` re-enters `execute()` fresh, so two callers retrying simultaneously coalesce again — consistent with the first call.

Cleanup deletes the map entry when the shared promise settles, using an **identity check**: delete only if the stored entry is still the one this call created. This mirrors the `DedupeTracker.clear()` fix from 2.1.0, where an unconditional delete let a late-settling superseded request wipe its successor's entry. The same mistake must not be re-made in a new tracker.

### Tests

Three simultaneous identical calls → one fetch, three identical Results; different params → no sharing; per-call headers → no sharing; per-call middleware → no sharing; one sharer aborts → it gets an abort Result while the others succeed; **all** sharers abort → the underlying fetch aborts; `share` + `dedupe` → throws at `createApi`, naming the request; a late-settling shared entry does not clobber a newer one; `share` composes with `retryMiddleware`; per-call `timeout` bounds only its own caller while the shared request continues for the others; per-request `timeout` bounds the shared operation for everyone.

## Feature 10 — Testing entry point

**Create** `src/testing.ts` and add a third export to `package.json`:

```json
"./testing": { "types": "./dist/testing.d.ts", "import": "./dist/testing.js" }
```

Tree-shaking keeps it out of production bundles, so it costs consumers nothing.

### Framework-agnostic by construction

**No test-runner dependency** — not vitest, not jest. The zero-dependency pillar applies here too, and a testing module that works under only one runner is worse than none. `mock.fetch` is a plain function:

```ts
vi.stubGlobal('fetch', mock.fetch)   // vitest
global.fetch = mock.fetch             // anything else
mock.install() / mock.restore()       // convenience, patches globalThis
```

### Mock at the fetch boundary

```ts
const mock = mockFetch({
  'GET /users/:id': ({ params }) => jsonResponse({ id: params.id, name: 'Ada' }),
  'POST /users':    jsonResponse({ id: '2' }, { status: 201 }),
  'GET /flaky':     [jsonResponse(null, { status: 503 }), jsonResponse({ ok: true })],
})
```

Stubbing `api.getUser` to return a canned Result was considered and rejected as the primary shape: it tests consumer code against a stub rather than against the library, leaving URL building, path substitution, header merging, body serialization, response parsing and consumer middleware unexercised. A test that passes while a `path: '/users/:userId'` typo ships is not doing its job.

Route keys are `"METHOD /path"` with `:token` matching — deliberately the same format as `tests/integration/server.ts`'s `callCounts`, so the library and its consumers share one idiom. A **handler function** receives matched params and the request; a **bare response** is static; an **array** is consumed in sequence, which is what makes retry, dedupe and share behaviour testable.

An unmatched route **fails loudly** — rejecting with a descriptive error naming the attempted method and URL — rather than silently returning a 404, which would look like a server behaviour rather than a missing stub.

### Assertions

```ts
mock.calls                          // [{ method, url, headers, body }] in order
mock.callCount('GET /users/:id')    // number
mock.lastCall('POST /users')        // most recent, or undefined
```

Enough to assert what actually went over the wire — the question a stubbed api object cannot answer.

### Result builders

```ts
import { successResult, errorResult } from '@iremlopsum/apify/testing'
```

Secondary, for consumers who do want to stub at the api level. Worth shipping now specifically because 3.0.0 turns `Result` into a discriminated union where `response` is non-null on success: anyone hand-rolling `{ data, error: null, response: null, retry }` today breaks on that upgrade, while anyone using the builder does not notice.

### Tests

Route matching including `:token` and method discrimination; unmatched routes failing loudly; response sequences advancing; `calls` / `callCount` / `lastCall` accuracy; `install()` / `restore()` leaving `globalThis` exactly as found.

## Risk

This is a larger release than 2.1.0. That was twelve small, independently verifiable fixes; this is four features with real design surface, and Features 2, 3 and 4 all touch the cancellation subsystem stabilised in 2.1.0 — a subsystem where three consecutive reviews each found a defect the previous one had not.

Mitigations: the typecheck prerequisite lands first and alone; each feature is independently testable; the existing dedupe and cancellation suites act as a regression harness and must pass untouched throughout; and every new test must be revert-verified (implement, revert `src/`, confirm the test fails, restore, confirm it passes) — 2.1.0 shipped one test that passed against unfixed code, and it was caught only by a reviewer reading it sceptically.
