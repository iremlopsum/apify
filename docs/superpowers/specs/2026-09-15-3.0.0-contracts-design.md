# apify 3.0.0 — "Contracts" Design

**Date:** 2026-09-15
**Status:** approved, ready for planning
**Supersedes:** [`../plans/2026-09-13-fixes-3.0.0.md`](../plans/2026-09-13-fixes-3.0.0.md), which predates 2.2.0 and 2.2.1 and is materially stale — roughly a third of it describes work already shipped. That document is input, not authority; it should be deleted once this spec has a plan.

---

## Goal

Make the library's type contracts true, unify the one subsystem that never fit the design, and close the last never-throws gap.

## Why now

Three things converged:

1. **The README has promised something false since 2.0.0.** It shows `if (error) return; data.name` and claims `data` is narrowed. It never has been — `data` and `error` are independent nullable fields, so the check buys nothing.
2. **`share` never fit the design.** The 2.2.0 whole-branch reviewer put it plainly: the cancellation subsystem "reads as four coherent mechanisms plus one bolt-on", and five separate findings trace to that one asymmetry.
3. **The safety net now exists.** 2.2.0 built a typecheck harness — 272 type tests in CI — precisely so a types-heavy release like this one could be done with a compiler doing the reviewing rather than a human.

## Scope

Three bodies of work, sequenced deliberately (see [Sequencing](#sequencing)):

- **Section 1 — Contracts.** Discriminated `Result`, phantom generics on `Request`, `ApiError.kind` required.
- **Section 2 — Cancellation unification.** `share` moves inside `execute()`'s spine.
- **Section 3 — Error model.** Parse failures keep their `Response`, `onError` suppresses aborts, GraphQL partial data, the fourth never-throws hole.

## Non-goals

- **Features.** Path-param inference, Standard Schema validation and pagination are deferred to additive minors after 3.0.0. They do not need a major, and holding them behind one delays them for no benefit.
- **Anything not already diagnosed.** Every item here has a verified reproduction. This release closes a known list; it does not go looking.

## Decisions already made

Settled during brainstorming. Do not relitigate without new information.

| Decision | Rationale |
|---|---|
| Scope is A+B+C, features later | C's restructure touches the same `onError` and error-construction code B changes; doing them apart means doing that region twice |
| Sequencing is Contracts → Unification → Error model | Section 1 is types-only, so it installs a compile-time safety net before the dangerous restructure; and C deletes code B would otherwise edit |
| `successResult`/`errorResult` migrate **silently** | They were shipped promising exactly this: "anyone hand-rolling a Result breaks on this upgrade; anyone using the builder does not". They also gain type-level tests so the shield is self-enforcing |
| Abort suppression is **central**, in `fireOnError` | One guard covers all call sites; no site has to remember |
| `SuccessResult.response` is **non-null** | Gives callers `response.status` with no null check on the success path. Costs middleware synthesising a success a `new Response(...)` — cheap and more correct |
| `'middleware'` is added as a sixth `ApiErrorKind` | A middleware throwing is a bug in consumer code, not a network failure; widening the union is what a major is for |

## Global constraints

- **Zero runtime dependencies.** Nothing may be added to `dependencies`, including test-runner packages.
- **Never throws.** Every public entry point returns a `Result`. The sole exception is `createApi`, which may throw on invalid configuration at construction. Closing the last exception to this is Section 3's job.
- **Pure ESM**, `.js` extensions on internal imports.
- **Runtime-agnostic.** No API with a floor above `engines` (`node >= 20`) or the browsers the README claims. `AbortSignal.any` and regex lookbehind both remain banned.
- **`src/index.ts` exports no utils or internals.**
- Test commands: `npm run typecheck`, `npm run test:types`, `npm run test:run`, `npm run test:integration`.

## Section 1 — Contracts

Types-only or near it. Zero runtime behaviour change. Its job is to install the safety net the next two sections lean on.

### The discriminated `Result`

```ts
export interface SuccessResult<T> {
  data: T
  error: null
  response: Response          // non-null — the server responded
  retry: () => Promise<Result<T>>
}

export interface ErrorResult<T> {
  data: null
  error: ApiError
  response: Response | null   // null for network, abort, timeout
  retry: () => Promise<Result<T>>
}

export type Result<T> = SuccessResult<T> | ErrorResult<T>
```

**All 20 construction sites already satisfy this.** Verified: every `createSuccessResult` call passes a real `Response` (`create-api.ts:566`, `graphql.ts:200`, `testing.ts:209`); every error path passes an `ApiError`. The union documents what the code already does. The three factories in `src/result.ts` keep their bodies; only their declared return types narrow to `SuccessResult` / `ErrorResult`.

Both members are exported from `src/index.ts` as types, so consumers can annotate either branch.

### Phantom generics on `Request`

```ts
declare readonly _params: TParams
declare readonly _response: TResponse
```

`Request<{id}, User>` currently accepts a `Request<{slug}, Post>`, because the class body never references its own generics and every instantiation is structurally identical. `Operation` in `graphql.ts` already does this correctly. `declare` emits no property, so the runtime cost is zero.

`ExtractParams` / `ExtractResponse` in `create-api.ts` resolve through the type reference and are unaffected — but this is the one thing in Section 1 that could plausibly regress inference, so it gets an explicit type test.

### `ApiError.kind` becomes required

Shipped as optional in 2.2.0 and already set at all seven construction sites. This is a one-line change — `kind?:` → `kind:` on `ApiErrorOptions` — breaking only for code constructing an `ApiError` directly, i.e. custom middleware.

### The testing builders

`successResult` / `errorResult` in `src/testing.ts` migrate silently: signatures unchanged, internals learn the union. They also gain type-level tests asserting they produce valid union members, so a future `Result` change cannot silently break the shield.

## Section 2 — Cancellation unification

### The problem

`share` sits **outside** `execute()` — lines 747–891, in the bare arrow body of the generated method — while `execute` spans 410–745 with its own catch and `.then` hook. The duplication is measurable: timeout resolution appears at three sites (463, 464, 806), `onError` fires from five (380, 724, 878, 881, 882).

### The invariant, made structural

2.2.1 established the right rule empirically, through two fix rounds and six measured cases:

> One report per **operation failure**, one per **caller give-up**, and a give-up that happens to abandon the operation is not also an operation failure.

Today that rule lives in conditionals spread across three call sites (`if (!wasLast)`, `if (!r.error)`, and a rejection handler). It works — but nothing in the structure says it, which is why it took two attempts and why the first attempt reported **zero** in two reachable configurations.

The unification expresses it once:

- `ShareTracker` aborts with a **distinguishable reason** when the last reference releases — *abandoned*, not *failed*.
- `execute`'s hook skips reporting for that reason.
- **Operation-level failure** (HTTP, network, parse, operation deadline) → `execute` reports, once.
- **Caller-level give-up** (this caller's signal or per-call timeout) → the per-caller wrapper reports, once each.
- **Abandonment** → nobody reports; every caller already did.

This **preserves** current behaviour rather than changing it. Three sharers hitting a 500 still produce one report, not three.

**How this interacts with Section 3's abort suppression.** Section 3 makes `fireOnError` skip `kind === 'abort'`, which at first reading contradicts the rule above. It does not: a caller give-up produces `'abort'` when its own signal fired and `'timeout'` when its per-call deadline expired, and only the former is suppressed. So after both sections land, the per-caller path reports **timeouts only** — its abort reporting becomes deliberately dead, and should not be deleted as such, because it is the same code path and the same invariant. The counts that change are precisely the abort rows of the 2.2.1 matrix, which drop to zero by design; the timeout rows are unchanged and remain the regression pin.

### What it retires

| Finding | How |
|---|---|
| Duplicate-`onError` conditionals | one sentinel check replaces three conditionals |
| `ShareTracker` dying-entry window | the tracker sets `dead` synchronously when it aborts, so `acquire`'s guard sees it immediately instead of waiting for `.finally()` |
| Signal-replacing middleware not re-merged with the share controller | share's signal goes through the same merge point as dedupe's, in `core()` |
| Three-way timeout duplication | one `resolveBudget(options, config)` returning `{ operation, perCaller }` |
| `share` outside `execute`'s try/catch | structurally inside it, rather than patched in |

### Risk, and why it is tractable now

This is the most dangerous change in the release. **Nine defects have been found in this subsystem across 2.1.0, 2.2.0 and 2.2.1** — every one passing its tests before a reviewer caught it.

Three things reduce the risk:

1. **Section 1 lands first**, so every Result the restructure produces is compiler-checked.
2. **The regression harness exists**: `dedupe.test.ts`, `dedupe-race.test.ts`, `dedupe-cache.test.ts`, `dedupe-signal.test.ts`, `share.test.ts`, `timeout.test.ts`, `retry-policy.test.ts` — and critically the **six measured `onError` counts** from 2.2.1, which pin the exact invariant being restructured.
3. **The semantics are known.** 2.2.1 established them empirically; this section makes the code say what it already does.

**Hard constraint:** the six `onError` counts and every cancellation suite must pass **untouched**. If one needs editing, the restructure changed behaviour — stop and report.

## Section 3 — Error model

### Parse failures keep their `Response`

A malformed body on a 200 currently falls into `core`'s network catch, producing `status: 0`, `response: null`, and a `SyntaxError` in `body` — indistinguishable from being offline, for a request the server answered fine.

`'parse'` has been declared-but-never-produced since 2.2.0, reserved so this release could emit it without widening the union. Parsing moves into its own try, emitting `kind: 'parse'` with the real status and a non-null `response`.

**Consequence to document:** a parse failure on a 503 now reports `status: 503`, so `retryMiddleware` will retry it where `status: 0` previously meant it did not. This is an improvement — a truncated response is worth retrying — but it is a behaviour change.

### `onError` suppresses aborts

One guard inside `fireOnError`, covering every call site. `'timeout'` deliberately still reports: a cancellation you caused is noise, a deadline you missed is a genuine failure. That distinction is why the two kinds were split.

### GraphQL partial data

When a response carries both `data` and `errors`, `gqlBody.data` is currently dropped. The GraphQL spec explicitly supports partial success.

It lands on **`error.partialData`**, not on `Result.data`. Populating both would break Section 1's union — `data` is non-null if and only if `error` is null is the property that makes `if (error) return` narrow.

### The fourth never-throws hole

An async middleware that throws rejects the caller's promise. Verified:

```
async middleware throws, non-shared path -> *** REJECTED ***: middleware exploded
```

`create-api`'s catch covers only synchronous setup; `composeMiddleware`'s dispatch has no guard. The share path was fixed in 2.2.0's final wave; the non-shared path — the common one — was not, and the gap is documented nowhere.

Fix: a rejection handler on the composed chain's promise, converting to a Result the way the sibling path already does. **Section 2's unification makes this one place instead of two.**

It produces **`kind: 'middleware'`**, a sixth union member. `'network'` would be inaccurate — nothing network-shaped happened — and a middleware throwing is a bug in consumer code you would want to fix rather than retry. Widening the union breaks exhaustive `switch` statements, which is what a major release is for.

### Documentation

The `response` body is consumed to produce `data`, so `await response.json()` throws *"Body has already been read"*. This is deliberate — cloning every response would cost a buffered copy for a re-read almost nobody performs — but it has never been written down. It goes in the README's Result section and the `ApiError` property table.

## Migration

`MIGRATION.md` exists with 2.1.0 and 2.2.0 sections; 3.0.0 adds a third. Unlike those, this one has real steps.

Breaking changes, each needing a before/after:

1. **`Result<T>` is a union, not an interface.** `data!` assertions and redundant null checks can be deleted. Middleware that *synthesises* a success Result must supply a non-null `Response` — `new Response(JSON.stringify(data))`.
2. **`Request` generics are no longer interchangeable.** Code assigning a mismatched `Request` stops compiling. That code was already wrong.
3. **`ApiError` requires `kind`.** Custom middleware constructing one must supply it.
4. **Parse failures changed shape.** Previously `status: 0`, `response: null`, `kind: 'network'`. Now the real status, a non-null `response`, and `kind: 'parse'`. Code branching on `status === 0` to mean "offline" should branch on `kind === 'network'`.
5. **`onError` no longer fires for aborts.** Hand-rolled `AbortError` filtering can be deleted.
6. **`ApiErrorKind` gained `'middleware'`.** Exhaustive `switch` statements need a new arm.
7. **GraphQL partial data** is now on `error.partialData`. Purely additive.

Include a "nothing to do if…" section: consumers who only call methods and check `error` need no changes beyond deleting now-unnecessary `data!` assertions.

## Sequencing

1. **Contracts** — discriminated `Result`, phantom generics, `kind` required, testing builders migrated.
2. **Unification** — `share` into `execute()`'s spine.
3. **Error model** — parse failures, abort suppression, GraphQL partial data, the middleware hole.
4. **Documentation and release** — README, CHANGELOG, MIGRATION.md, version.

The order is *install the safety net, then do the dangerous thing, then do the behavioural thing on simplified code.*

## Testing strategy

- **Revert-verify every new test.** Three tests on this project have been caught passing against unfixed code, twice despite the constraint being written down. For each new test: make the fix inert, confirm it fails, restore, confirm it passes.
- **The six `onError` counts from 2.2.1 are the invariant for Section 2** and must pass untouched.
- **Type-level tests carry Section 1**, including the README's headline example compiling, and an explicit test that `ExtractParams`/`ExtractResponse` inference survives the phantom generics.
- **Every README example must compile** under `tsc --noEmit --strict`.
